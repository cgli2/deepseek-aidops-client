# 超长任务协同编排与容错自愈架构设计方案 (Long-Horizon Autonomous Orchestration Architecture)

## 1. 概述与背景

随着智能体（Agent）面对的工程任务复杂度急剧上升，大量任务（如大型代码库重构、全自动化端到端测试与修复、全链路系统仿真等）的执行周期从传统的秒级/分钟级延伸至**数小时甚至数天**。

在超长运行周期下，传统的单体 Agent 循环（ReAct Loop）或简单线性重试机制必然面临以下根本性瓶颈：

1. **上下文窗口爆炸与注意力稀释**：长时间运行后历史 Token 迅速填满，上下文衰减导致严重幻觉与偏离原始目标。
2. **单点脆弱性与级联崩溃**：任何单次网络抖动、模型超时、Rate Limit（429）或 Worker 崩溃都会导致整个任务直接夭折。
3. **协作阻塞与并发死锁**：多任务缺乏清晰的依赖与隔离边界，数据竞争与状态不一致频发。
4. **交付质量不可控**：执行数小时后缺少阶段性门禁，最终产物出现隐蔽缺陷导致全盘返工。

本设计方案 v1.0 提出了一套**基于「事件驱动 DAG 编排 + Actor 协同 + Saga 状态持久化 + 分级续命自愈 + 质量门禁」的超长任务分布式架构（LHA-Arch）**。

> **v2.0 修订：升级为 DRLA（Durable Resilient Long-Horizon Architecture）**。v1.0 的宏观编排骨架（DAG 调度 / 租约续命 / 黑板解耦 / 质量门禁）保留有效；经深度推导发现六大隐藏工程缺陷，v2.0 以"确定性基座包裹概率性智能核心"为哲学，引入五大新机制逐一修复。

### v1.0 六大隐藏缺陷（v2.0 修复目标）


| 编号 | 缺陷                                                  | 等级 | 根因                                      |
| ---- | ----------------------------------------------------- | ---- | ----------------------------------------- |
| D1   | 非幂等物理副作用：崩溃重试在脏工作区续跑，级联失败    | 致命 | 逻辑状态（WAL）与物理文件副作用无事务边界 |
| D2   | 有损上下文漂移（Epistemic Drift）：滚动摘要稀释硬约束 | 致命 | 叙事记忆与不可压缩的硬约束事实混轨处理    |
| D3   | 语义级合并踩踏：文本零冲突但 AST/类型契约断裂         | 高危 | 行级三方合并不感知语法树与类型系统        |
| D4   | 自愈死循环振荡：修复 A 引发 B、修复 B 改回 A          | 高危 | 修复回路缺乏单调收敛判定                  |
| D5   | 不可逆决策滞后：早期关键决策错误后期才发现，全量回滚  | 中危 | 关键决策点无检查点与影子验证              |
| D6   | 预算失控：Rate Limit 风暴与 Token 黑洞                | 中危 | 缺乏全局预算控制器与反压联动              |

### v2.0 五大新增核心机制

1. **CoW 事务沙箱 + 两阶段提交**：每个 Worker 运行于写时复制（Copy-on-Write）沙箱，物理副作用先暂存、后原子提交，崩溃自动丢弃半成品，保证幂等重试（修复 D1）。
2. **双轨结构化事实矩阵**：自然语言摘要轨（可压缩、有损）+ 结构化 KV 硬约束轨（不可压缩、全量重放），每次任务装配时注入全部不变式与验收标准（修复 D2）。
3. **AST 接口契约锁**：基于 Tree-Sitter 提取公共接口签名并上锁，并行分支合并时在语法树层校验跨模块契约，阻止"文本无冲突、编译失败"的静默破损（修复 D3）。
4. **Lyapunov 能量单调收敛门禁**：为修复回路定义能量函数 E（缺陷数 × 权重的加权和），仅允许能量下降的修复动作，能量超阈���即冻结并回滚到上一稳定快照（修复 D4）。
5. **内容寻址 MVCC 工件库 + 影子 HITL 检查点**：工件以 BLAKE3 哈希寻址、不可变、多版本并存；早期不可逆决策设影子人机验证检查点，避免后期全量回滚；全局预算控制器与 Token 桶反压联动（修复 D5、D6）。

> **v2.1 评审修订（有条件通过）**：经评审与假设推演验证，v2.0 骨架有效；推演发现 7 项残余问题（R1–R7），其中 R1/R2/R4/R7 为通过条件，须补齐后方可进入实施。

## 3. 核心机制详解

### 3.1 动态任务拆解与自适应 DAG 编排（Decomposition & DAG）

长任务不能做一次性静态全量拆解。由于数小时的运行过程中会产生大量不可预知的中间结论与环境反馈，系统采用**分层任务网络（HTN）+ JIT（Just-In-Time）局部伸缩 DAG**。

#### 1. 分层拆解模型

- **L1 战略级里程碑（Milestones）**：规划长周期宏观交付路径（例如：需求分析 $\to$ 架构定义 $\to$ 分模块并行实现 $\to$ 系统联调 $\to$ 综合测试验收）。
- **L2 战术级子任务单元（Task Units）**：将每个 Milestone 分解为具有清晰数据流向和依赖关系的无环图节点。
- **JIT 动态演进**：下游节点的具体子任务不预先静态固定，而是在上游产出工件（Artifacts）后，由 Planner 结合最新真实上下文动态展开子图。

#### 2. 自包含子任务契约（Subtask Contract）

每个子任务必须是**自包含、有边界、可验证、幂等**的独立单元：

```json
{
  "task_id": "task-phase2-codegen-003",
  "parent_id": "milestone-phase2",
  "dependencies": ["task-phase2-design-001"],
  "inputs": {
    "specs_uri": "vault://artifacts/phase2/spec_v1.json",
    "context_summary": "已完成数据结构定义，本任务仅负责实现 RPC 序列化模块"
  },
  "invariants": [
    "不得修改 shared_kernel/ 目录下的已有接口",
    "单测覆盖率须 >= 85%",
    "静态分析零 Lint Error"
  ],
  "expected_output_schema": "ArtifactRef",
  "timeout_seconds": 900,
  "max_retries": 3,
  "retry_backoff": "exponential"
}
```

---

### 3.2 智能分发与多 Agent 协同机制（Dispatching & Collaboration）

#### 1. 基于角色能力的自适应路由（Capability-Based Dispatching）

- **Worker 角色矩阵**：
  - **Planner Agent**：专注任务分解、拓扑修正与动态重规划。
  - **Coder/Worker Agent**：专注在隔离沙箱内进行编码与工具执行。
  - **Verifier/Critic Agent**：独立执行单测、静态检查与 Invariants 合规审计。
  - **Aggregator Agent**：负责冲突合并、工件汇总与上下文精简。
- **调度打分算法**：调度器综合评估 Worker 当前负载、Token 消耗速率、模型能力评级（如 Fast-LLM / Code-LLM / Reasoning-LLM）及工作区文件亲和度（Affinity Cache），将就绪任务分配至最佳 Worker。

#### 2. 黑板模式通信与工件解耦（Shared Blackboard & Artifact Vault）

- 严禁多个 Agent 之间直接进行冗长的全量上下文对话。
- 统一采用 **Blackboard Pattern（黑板模式）**：
  1. Worker 完成任务后，将全量产物（代码补丁、测试报告、日志）存入 **Artifact Vault**。
  2. Worker 仅向黑板发布标准事件通知 `TaskCompletedEvent(task_id, artifact_uri, summary_diff)`。
  3. 下游 Worker 仅按需拉取对应 `artifact_uri` 与轻量级结构化上下文，彻底杜绝上下文污染与级联膨胀。

### 3.3 超长任务“存活续命”与容错自愈体系（Liveness & Fault Tolerance）

```
        ┌─────────────────────────────────────────────────────────┐
        │                 Worker 正在执行长子任务                 │
        └──────────────────────────┬──────────────────────────────┘
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
   【周期性心跳与租约续期】                   【增量 Checkpoint / WAL】
   - Worker 发送 Heartbeat Ping              - 局部执行状态写 Snapshot
   - Scheduler 更新 Lease 过期时间           - 暂存中间文件 / 进度台账
              │                                         │
     ┌────────┴────────┐                                │
     │ 心跳超时/Worker挂死                              │
     ▼                 │                                │
【哨兵 Watchdog 介入】  │                                │
 - 回收任务所有权       │ (正常续期中)                   │
 - 标记当前 Worker 故障 │                                │
 - 触发崩溃恢复 ───────┼────────────────────────────────┘
                       ▼
         【从最新 Checkpoint 恢复调度】
         - 提取已确认的中间工件
         - 清理未提交的脏状态 (Rollback)
         - 换由新 Worker 重新执行 / 续跑
```

#### 1. 动态租约与心跳哨兵（Lease & Watchdog）

- **租约（Lease）机制**：Worker 认领任务时获得短期租约（例如 3 分钟有效）。
- **Keep-Alive 自动续期**：Worker 在执行过程中周期性向中枢发送进度心跳，心跳正常时租约自动顺延。
- **僵尸任务回收**：若因 OOM、网络中断或死循环导致心跳停止，Watchdog 在租约到期后自动回收任务所有权，并将任务重新投递调度。

#### 2. 增量快照与上下文压缩（Checkpointing & Epistemic Compression）

- **增量快照（State Snapshot）**：每个子任务在关键动作后将中间状态（文件变更暂存、执行进度元数据）持久化。
- **认知压缩与窗口复位**：当子任务的 Token 消耗逼近安全阈值时，自动触发总结蒸馏机制：将过往细碎的 Tool Call 过程提炼为 `State Transition Ledger`（状态流转台账），复位并加载全新 Clean Context 继续执行，打破单次上下文上限。

#### 3. WAL 与崩溃零丢失重放（Write-Ahead Logging）

- 调度引擎的所有状态变迁（任务创建、派发、完成、失败、依赖满足）全部先写 **WAL（预写式日志）**。
- 若主控服务发生硬件断电或进程重启，服务启动时重放 WAL 日志即可毫秒级重建 DAG 拓扑与执行状态，已完成的数小时工作绝对零丢失，直接无缝继续后续任务。

---

### 3.4 全局自适应调度与并发反压引擎（Adaptive Scheduler & Backpressure）

#### 1. 拓扑就绪队列（Ready Topological Queue）

- 调度器实时跟踪 DAG 依赖矩阵。当某个节点的所有父依赖都进入 `COMPLETED` 状态时，该节点立即激活并推入优先级就绪队列。
- 支持**硬依赖（Hard Dependency）**与**软依赖（Optional Dependency）**，支持动态条件分支（Conditional Branching）。

#### 2. 自适应流控与反压（Adaptive Rate Limiting & Backpressure）

- **全局 Token 速率控制器（Token Bucket & Leaky Bucket）**：实时监控各 LLM 厂商的 TPM（Tokens Per Minute）与 RPM（Requests Per Minute）水位。
- **429 智能退避与降级**：出现限流警告时，自动启动带有 Jitter（随机抖动）的指数退避策略，或动态将次要任务路由至备用模型/节点，避免任务大面积超时雪崩。

---

### 3.5 最终结果汇聚与交付质量门禁（Aggregation & Quality Gate）

长任务的最终目标是高置信度的完整交付，必须杜绝“过程看似成功、最终产物无法运转”的假完成现象。

```
              ┌───────────────────────────────────────┐
              │          各并行分支产物生成           │
              │  (Artifact A, Artifact B, Artifact C) │
              └───────────────────┬───────────────────┘
                                  │
                                  ▼
              ┌───────────────────────────────────────┐
              │          Map-Reduce 工件汇总          │
              │   - 代码合并与 Git Conflict Resolve   │
              │   - 产物跨模块依赖一致性校验          │
              └───────────────────┬───────────────────┘
                                  │
                                  ▼
              ┌───────────────────────────────────────┐
              │          多层质量门禁 (Gate)          │
              │  1. 静态检查 (Linter, Typecheck)      │
              │  2. 构建与单元测试 (Build & Unit Tests)│
              │  3. 端到端集成测试 (E2E Tests)        │
              │  4. 不变式审计 (Invariants Check)     │
              └───────┬───────────────────────┬───────┘
                      │ 合格                  │ 发现缺陷
                      ▼                       ▼
          ┌───────────────────────┐   ┌───────────────────────┐
          │     最终交付打包      │   │ 触发局部自愈/Refine   │
          │ (Release & Final Log) │   │ (带失败诊断的局部重试)│
          └───────────────────────┘   └───────────────────────┘
```

#### 1. 分支工件聚合（Map-Reduce Aggregator）

- 各并行分支完成的代码与配置由 Aggregator 统一合并，通过自动三方合并（Three-way Merge）解决非冲突部分，若有冲突则自动唤起专职 Conflict Resolver 进行语意消解。

#### 2. 分级质量门禁（Multi-Tier Quality Gate）

- **Tier 1 - 静态规约门禁**：编译通过、语法正确、无类型错误、文件目录结构符合规范。
- **Tier 2 - 功能验证门禁**：全量单元测试与集成测试通过率 100%，无回归破损。
- **Tier 3 - 不变式与合规门禁（Invariants Verification）**：核对核心接口、安全性、性能约束是否保持不变。

#### 3. 失败回路与闭环自愈（Self-Healing Loop）

- 若质量门禁未通过，门禁系统将报错堆栈、日志以及失败的最小测试用例打包为 `Diagnostic Context`，在 DAG 中动态注入一个修复节点（Refine Task），进行针对性自愈重试（最多设定重试次数），重试失败则触发 HITL（人机协同接入）保护现场。

## 4. 关键数据结构设计

### 4.1 任务节点状态机（Task State Machine）

```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub enum TaskStatus {
    Pending,                      // 初始状态，等待依赖满足
    Ready,                        // 依赖已满足，在调度队列中
    Scheduled { worker_id: String }, // 已派发给 Worker
    Running { lease_expire_at: u64 }, // 执行中，具有有效租约
    Validating,                   // 产物生成完毕，正在执行门禁校验
    Succeeded { artifact_uri: String }, // 校验通过，任务完成
    Failed { reason: String, retry_count: u32 }, // 失败
    Cancelled,                    // 被取消
}
```

## 5. 总结与落地价值


| 维度               | 传统单体 Agent 机制                | 本方案（LHA-Arch）                                 |
| :----------------- | :--------------------------------- | :------------------------------------------------- |
| **可支撑运行周期** | 10 ~ 30 分钟（易上下文衰减或超时） | **数小时至数天（分段隔离、无限续命）**             |
| **并发与协同**     | 串行或弱同步，易竞争与状态混乱     | **DAG 拓扑解耦 + 黑板事件驱动 + 幂等工件**         |
| **抗单点故障能力** | 单点中断则整任务失败，无状态重放   | **WAL 增量持久化 + 租约心跳哨兵 + 毫秒级断点续跑** |
| **Token 控制效率** | 全量历史线性堆积，超大上下文开销   | **子任务自包含窗口 + 认知压缩 + 按需工件引用**     |
| **最终交付保证**   | “尽力而为”，缺乏可靠验证         | **多层 Quality Gate 门禁 + 不变式校验 + 闭环自愈** |

本架构为复杂、长周期的重大自动化研发与运维任务提供了系统级工程保障，实现了超长任务的高效拆解、低耦合协同、不中断存活与确定性质量交付。
